# خطة النشر والتحقق والـ Rollback غير المدمّر (Zero-Destruction Protocol)

> **تاريخ التحديث:** 25 أكتوبر 2026  
> **حالة النظام:** جاهز للنشر بانتظار الموافقة المكتوبة الصريحة ("تمام")  
> **القاعدة الصارمة الحاكمة:** ممنوع نهائياً أي DROP أو TRUNCATE أو DELETE على أي جدول حقيقي، وممنوع أي استرجاع ماسح (`--clean` أو `CASCADE`). المسموح فقط: UPDATE لتصحيح الروابط أو الفروع، و INSERT عند اللزوم.

---

## 1. التزام السلامة الصارم (Safety Mandate)
- **قاعدة البيانات الحالية (`public`) تحتوي على بيانات المحل الحية وشغّال بيها.**
- الإجراءات المسموح بها فقط:
  1. القراءة (`SELECT`).
  2. الإضافة السليمة (`INSERT`).
  3. التعديل الموجّه لتصحيح الروابط أو الفروع (`UPDATE`).
- **أي حذف لأي سجل يتطلب وقوفاً واستئذاناً صريحاً مع عرض البدائل الآمنة أولاً.**

## 3. خطة النسخ الاحتياطي والاسترجاع الموحّدة (SQL Format Only)

### أ. ملفات النسخ الاحتياطي المعتمدة:
1. **النسخة السابقة للـ Migration:**  
   `backups/accessories_store_backup_pre_migration_2026-10-24T18-36-19-142Z.sql` (1.39 MB).
2. **النسخة الحية قبل النشر مباشرة:**  
   سيتم أخذ نسخة SQL عادية كاملة (Plain SQL) محددة صراحة بـ `--schema=public` من قاعدة البيانات الحية فقط لمنع أي تسريب لأي schema تجريبية:
   ```bash
   pg_dump "$DATABASE_URL" --schema=public --no-owner --no-acl -f "backups/accessories_store_pre_deploy_live_$(date +%Y%m%d_%H%M%S).sql"
   ```

### ب. خطوة التحقق الإلزامي من الـ Backup قبل النشر (Dry-Run Verification):
- فور أخذ ملف الـ SQL:
  1. يتم استرجاعه على قاعدة بيانات مؤقتة منفصلة: `accessories_restore_temp`.
  2. مقارنة وتأكيد عدد السجلات في كل جدول ومطابقة إجمالي الفواتير (يجب أن يطابق 100% ما هو مسجل في `public` الحية).
  3. بعد نجاح التطابق فقط، يُسمح ببدء خطوات النشر.

### ج. الـ Rollback غير المدمّر (Zero-Destruction Protocol):
- **تم شطب وإزالة أي أمر استرجاع يتضمن `DROP SCHEMA public CASCADE` أو `--clean` نهائياً.**
- **في حال حدوث خلل برمجي:**  
  الرجوع للنسخة البرمجية السابقة بـ Git فقط (`git revert` أو تفعيل deployment سابق على Render/Vercel) دون لمس قاعدة البيانات.
- **في حال حدوث خلل في البيانات:**  
  تصحيح محدد عبر استعلامات `UPDATE` موجّهة ومكتوبة بدقة للسجلات المتأثرة.
- **في حال لزم استرجاع سجلات مفقودة من Backup:**  
  الاسترجاع يتم على الداتابيز المؤقتة `accessories_restore_temp`، ثم عمل Diff ومقارنة، وسحب ونقل السجلات المطلوبة فقط عبر `INSERT ... ON CONFLICT DO UPDATE` إلى `public` الحية، دون حذف أي بيانات حية سارية.

## 5. جدول التحقق اليدوي بعد النشر (Post-Deployment Checklist)

> ⚠️ **تنبيهات مشددة:**  
> - **ممنوع نهائياً إصدار أي فاتورة تجريبية على الداتابيز الحية (لأنه لا يمكن حذفها).** اختبار الـ POS يتم بفتح الشاشة ومطابقة الأصناف والأسعار.  
> - فرع `b1` هو **أحمد عرابي** وفرع `b3` هو **فرع 3**، كلاهما فارغ (0 منتجات). أي إضافة منتج فيهما تتم بمنتج حقيقي يطلبه العميل لاحقاً.  
> - الاختبار يتركز على الفروع التي بها منتجات فعلية: **فرع b4 (المكتب)** و **فرع b2 (المديرية)**.

| **1. الفحص العام** | عام | فتح رابط الموقع و `/health` | استجابة `200 OK` وسرعة تحميل الواجهة |
| **2. فحص فرع المكتب (b4)** | كاشير المكتب (b4) | تسجيل الدخول وفتح شاشة POS | ظهور المنتجات والأسعار والتأكد من فواتير اليوم الـ 4، دون الضغط على حفظ فاتورة جديدة |
| **3. فحص فرع المديرية (b2)** | كاشير المديرية (b2) | تسجيل الدخول وفتح شاشة POS | ظهور منتجات وأسعار فرع 2 الخاصة به فقط، وثبات شاشة البيع |
